# Playbook · 严重度、owner 路由与派单

具体的人名、领域表、「核心功能」清单在领域 pack 里；这里是通用方法。

---

## 1. 严重度：机械化的三问（同一张票评 N 次必须同一结果）

| Q1 系统坏了 / 数据错了？ | Q2 影响面 | Q3 核心功能？ | 级别 | SLA（工作日） |
|---|---|---|---|---|
| 否 | — | — | P2 | 7 |
| 是 | 多 | 核心 | **P0** | 1 |
| 是 | 单 | 核心 | P1 | 3 |
| 是 | 多 | 非核心 | P1 | 3 |
| 是 | 单 | 非核心 | P2 | 7 |
| 需求 / 实验设计类 | | | P2 | 无 SLA（不要自己编日期） |

- **核心** = 数据正确性、主要业务数字、核心流程、对外导出、计费 / 财务（具体清单由领域 pack 定义）；**非核心** = 格式、导航、筛选、提示、颜色。冲突时算核心。
- **Q2 的证据 = 工单 ∪ 实测**。工单是下限；实测 `count(distinct 实体)` ≥2 → 多。禁止「理论上可能影响所有人」。
- **升级闸**（缺陷成立之后，任一命中 → 多）：根因在不按实体分支的共享层（附计数）· 证据里已经有跨实体实测计数 · 触发是平台级变更（切换、迁移、发布、全局开关、厂商账号级管控）。
- **共享层闸**：工单只列了一个实体时，如果涉及全局字典、共享视图 / 模型、对所有实体运行的定时节点、前端常量、指标库 / API 契约、全局配置 / 白名单 → 先数影响面再填 Q2。
  自检：「修好这一行，会不会顺便修好别人？」
- 数不清 → 只能写 `single`，置信度 ≤ 中，标 `scale_unverified`。例外：配置 / 权限变更类根因的单位是「操作者 × 被拦动作」，不是实体数。
- 缺陷成立之前，受损面 = 0（「共享、无实体分支」也可能只是在描述统一的产品行为）。
- **证据变了就重评**，记录 `re-rated: 旧 → 新, artifact=…`；降级同样要证据。
- 文字（「所有客户」）和评级（P1 = 单）要一致。工单自带的优先级是别人的结论，不是输入。
- 影响面报三个数：受损面（驱动派单和 SLA）/ 暴露面（共享同一表达式但现在没发作）/ 修复爆炸半径。
- 输出契约：第一行是严格单行 JSON（便于外层解析），后面是人读的评分逻辑。评级 skill **只评级，不做写操作**。

## 2. owner 路由

- 路由表的每一行：领域 × 示例范围 × **谁来修（第二负责人）** × **谁拍板（PM）** × 边界备注（记录历史上路由错的情况）。
  另有：同名歧义表、**已知空缺登记**、兜底 owner。
- PM 在故障类里可选（「坏了」从不拉 PM）；在口径 / 可比性和需求类里必选。PM 要来自你判定的领域，不是来自工单里的某个词。拿不准就不拉（缺了只是慢，错了是打扰）。
- **领域 owner ≠ 这次的执行者**。找执行者三步：子领域那一行 → 上次谁做的（搜聊天 / owner 台账里「不在名单上但实际接了」的人）→ 「没找到 <动作> 的执行者，请 <领域第二负责人> 指定」并登记空缺。
- 只在**已观察到**的共性上升级（「我能说出第二个实例吗？」），不在代码可达的共性上升级。根因在共享层 → 加上该共享文件最近的作者（`git log -- path`）。
- 不要把兜底的人（我）当成转派目标；用领域第二负责人。
- owner 台账：结案后对比「@ 了谁」vs「实际谁接了」，学习结果作为路由修改**建议**，由人批准。

## 3. 派单与交接

**切分**：按数据路径切，不按问题切 —— 入口与筛选 → 采集 → 判定与归一 → 写入闸 → 读取与展示，加上横切的编排 / 可观测和凭据 / 权限。
每个问题只归一个领域；跨领域的问题切成几块。领域之间只通过明确的数据契约（字段、取值范围、状态语义）对接，所以能独立测试。

**派发顺序**：0 测试资产（金标准、向量、fixture、测试记录、harness）→ 1 无外部依赖的领域 → 2 依赖契约的领域 → 3 读取层 + 集成 + 端到端 → 4 回填 + 需要人做的架构决定。
对同一份产物的并行修改在副本里做，由集成者按固定顺序合并，每次合并后重跑该领域的单测。

**交接模板**（别人的服务、大爆炸半径、迁移、需要更高权限、≥10 个实测受影响实体、任何要别人动手的修复）：
1. 症状（一行 + ID + 时间窗）
2. 已确立的事实（带证据）
3. 需要谁做什么（写目标，不写实现；实现选项放进三档菜单）
4. 临时影响
5. 当前状态（四态）
6. 验收条件（可运行、针对原症状）
7. 执行者（具名）

**三档修复菜单**：列 = 档 · 动作 · 层 · 决策类型 · 拍板人 · 前置条件 · 工作量 · 失效期。
档 = 带失效期的局部 hack / 正式修复 / 重改造。按杠杆排序，不按成本排序（架构切换往往最便宜）。
必含：反复失败 → 要有「执行架构改造」一档；输出偏离真值 → 要有「重跑离线生产者 + 回填」一档；双轨配置 → 要有「单实体私有线路」一档。

**派单前确认**：谁已经在推（别重复）、客户状态（例如流失风险 → 低优先级的需求往后放）、团队可用性（时区、假期）。
小分母告警可能不需要动作，建议等而不是制造工作。同一个手工修复做了 3–4 次 → 该写通用 SOP 了。

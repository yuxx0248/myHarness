# Playbook · 排查诊断

适用：故障、告警、「数对不上」、「为什么没生效」、任何需要找根因的事。
领域细节（表名、服务、SQL、系统清单）不在这里，在领域 pack。

---

## A. 主流程（每步都有停止条件，跳步就是历史上每次误判的来源）

1. **入门三问（30 秒）**：症状（看到了什么值 / 报错 / 缺失）· 表面（哪个页面 / 服务 / 任务 / 告警）· 手上已有的证据（ID、链接、截图、commit）。
   缺一项就问，不要编。看到**危险标识**（长度不对的 ID、陌生的表后缀、分支没前缀）→ 先停，别跑任何写操作。
2. **读诉求，不只读症状**：先判断请求动词 ——「坏了 / 对不上」（故障）、「做 / 加 / 覆盖」（需求：诊断 + 范围选项，不修、不给日期）、
   「解读 / 验证 / 这是什么意思」（分析：给结论，不给修复）、「设计 / 怎么测」（设计：给方案和作者）。
   **先写一行：「这件事交付的是 ____」。**
3. **先看真实输入**：工单有附件 / 导出 / 截图 → 先下载核对（那是「客户实际所见」）。判断「空 / 零」用权威计数列，不用派生列。
4. **先查人和历史**：扫相关群近 24–48h（已否决 / 已确认 / 有人在做）；grep FAQ 和纠正记录 —— **命中只算起点假设**，要在本地重新验证。
   同一件事已经有人在推进 → 同步进度，不要重复初判。
5. **先排除「还在跑」，再排除「其实要的是分析」**：「进行中」长得和所有失败都一样，错判代价最高，所以第一个排除。
6. **先画图再假设**：数据 / 控制流（源 → 各层 → 表面）。标 `?` 的边不能承载根因推理。有多个版本 / 并行 / 冻结副本时，先确认哪个是线上在用的。
7. **先确认「设计如此」的部分**：刷新节奏（日批还是准实时）、约定（周起始日、窗口、取整）、模型的声明输出。
   不知道设计常态之前，「延迟 N 小时」「两列不一样」什么都说明不了。
8. **拿机器证据**：复现、跑工单本身的查询、拉日志。至少有一条机器输出之前，不说「我觉得 bug 是…」。
   验证要走 bug 的**真实路径**；干净路径通过不算数；无法复现时用工单的真实数字模拟，并标明是模拟。
9. **分层状态表**：`层 | 期望 | 实际 | 状态 | 备注`，第一个 ❌ 的层是嫌疑层，集中看它和它的上游一层。分层对照要在**同一条查询、同一个快照**里做。
10. **时间锚定**：找到**被报告的那个量本身**的断点（按实体 × 天取 `MAX(date)` → 换算 `lag_days`），列出断点 ±1 周期内的变更（迁移、schema、配置、发布）。
    配置要按「报告时」从变更历史还原，不能拿现值推过去。拿断点去全平台扫「那天还有谁断了」，再看**没断的那一半**（存活分流）。
11. **≥3 个可证伪的假设**，按杠杆排序，每个配一个 ≤5 分钟的证伪查询。不能证伪的假设删掉。
    默认先怀疑：配置先于代码；输入 / 参数先于算法；环境 / 额度 / 权限先于逻辑；部署元数据先于本地代码；回归先看最近的提交。
12. **证因果，不只证存在**：「如果 X 是原因，那 X 不成立的地方症状就该消失」—— 跑这条查询。反例必须正面解决，不许合理化。
13. **对照组 / 探针矩阵**：同一视图里的兄弟键、同一实体的其他来源、同一来源的其他实体、干净实体、换一个资源池跑同一条查询。
    间歇性 / 性能问题至少 4 行，每行只变一个变量；两行不足以下因果。
14. **每个假设标 ✓ / ⚠ / ✗**。任何承重的 ⚠ 都是停止条件；置信度跟着最弱的承重环节走。
15. **根因要有执行者**：`<具名组件/节点/file:line/表.列> 在 <条件> 下做了/没做 <X>，导致 <下游字段> 取值 <值>`。
    主语是现象（「模型高估」「流水线坏了」）= 还在症状层，不要分类、不要派单。
16. **拆开独立断言**，各自给产物和置信度：根因 · 影响面 · 修复 · 状态 · owner。对一个不代表对另一个。
17. **发送前过闸**（见 `verification-and-closure.md`）：误报 / 定性闸、因果方向闸、影响面闸、结案闸。
18. **选输出形式**：自己领域 → 一行最小 diff；别人的服务 / 大爆炸半径 → 交接模板；≥2 种修法能消除症状 → 三档修复菜单；卡住 → 「还缺什么」出口。
19. **把「下次怎么发现」也修了**：skill 关键词、锁定不变量的代码注释、SOP 案例、告警新增或调整。
20. **复盘**：根因翻了几次、哪些 30 秒验证没跑、哪些 owner 没问 —— 每次翻转都是一个 SOP 规则缺口的候选。

### LLM 自己特有的偏差（主动防）
往故事方向推理 · 长上下文里的确认偏差（把我的「是不是 X？」当成重新开始的信号）· 过早收敛（「残差约 $5K」式的含糊带过）·
死胡同合理化（对着空缺讲故事）· 名字驱动的假设（去追真正的写入者，不追表名）· 没找到就放弃 ·
**排除法跳到看不见的层**（「我能查的都查了，所以一定是我查不了的那层」）· 把「非成功」读成「失败」。

## B. 认知陷阱目录（16 类，每类 = 陷阱 → 防护）

| # | 陷阱 | 防护 |
|---|---|---|
| T1 | **设计行为被当成故障**：前提从没被检查，后面每步都自洽所以显得很确定 | 先确认设计的节奏 / 约定 / 声明输出；「配置里没有」≠「忘了配」；找意图证据（首次引入的 blame、PRD、owner 一句话），没有就写「意图未决 → PM」。链条越长越要回头查第一个前提 |
| T2 | **进行中被当成失败**（镜像：断言「会自愈」） | 写「失败」必须有：编排器终态行 / 写入方错误日志 / 没有运行实例且超过 p95。否则只能写「尚未成功，终态未知」。写「会自愈」要给回填速率基线 + 预计完成时间 + 复查查询 |
| T3 | **最显眼、证据最多的对象被当成起火点**（拥塞、堆积） | 只算同一个池里的占比（<20% 不能叫主因）；先定 T0，晚于 T0 开始的是果；比自身基线慢很多的是受害者；反事实：「删掉它 T0 还会堵吗」；止血对象 ≠ 根因，分两句写；重试风暴按定义就是果 |
| T4 | **机制存在 ≠ 机制是原因**（静态缺陷被当成本次原因） | 三态表：从没读到 / 读了但这次失败 / 读到了真坏值，划掉两格要有证据；自问「我的根因能解释『刷新一下就好了』吗」；分配表做守恒检验；静态缺陷单列，证据标准同主因 |
| T5 | **根因 / 修复放错层** | 配置先于代码（值 + `updatedAt` + 上次成功时的值 + 回滚重跑对照）；登记 ≠ 生效 ≠ 已回填；同一层被证伪两次 → 换层；公共规则 vs 私有覆盖要落到行；「我们自己有按钮 / API 能按吗？」没有 → 厂商控制面 |
| T6 | **影响面从 1 例放大成全量** | 影响面是独立断言；三层：代码可达 / 已观察 / 声称（默认 = 已观察）；扩到「所有」需三选二：第二个独立实例、量级对账、穷举入口；把受损面 / 暴露面 / 修复爆炸半径拆成三个数 |
| T7 | **影响面被压缩成工单表面**（严重度评低） | 影响面 = 根因层的消费者；工单只是下限；共享层闸：「修好这一行会不会顺便修好别人？」；数不清就只能 `single` + 置信度 ≤ 中 + `scale_unverified` |
| T8 | **比较 / 测量读数被当成计算坏了** | 入口测试：「单独拿任意一个对象，还异常吗？」不异常 → 是比较类：列对象差异表、归一到同口径重算；声明输出先分解，只有残差才是缺陷候选；实验的 0 先问「是算出来的还是测出来的」 |
| T9 | **二手声明被当成观察事实** | 引用前重算（生产者、时间戳、输入对账、同公式重算）；别的系统的自述要在取证时重新问一次、查它们的仓库 / PR；快照不能证明历史；继承的报告一律 ⚠ |
| T10 | **时间轴盲区**（没断点、没 as-of、没存活分流） | `MAX(date)` → 减法 → 再用形容词；「最后一天 ≈ 报告日」是断裂指纹；已结算的历史不会因现实事件改变 → 是回填或模型重解；我的配置行没变 ≠ 没有变更事件 |
| T11 | **在错误的通道上排除了变更** | 列出一个操作的所有下游通道（投放 / 度量 / 状态消费者），逐一证伪；独立性按通道数，不按条目数 |
| T12 | **没逐条核对就驳回对方的前提** | 把对方的话拆成独立断言；对每条给出我方所有同窗口度量；有任何一个同向 → 现象存在，进根因，不要要截图；置信度倒挂本身就是警报 |
| T13 | **定性 / 承诺越权**（两个方向）+ 旁支泄漏到客户 | 两个方向的定性都需要 PM + owner；观察 / 定性 / 动作三栏；承诺动词检测：删掉时间词还是承诺吗？客户可见的每句话都要回答客户的问题 |
| T14 | **状态报错**：已修报成待修、待修报成已修、开关当验收、workaround 当结案 | 四态状态位；每个「已…」有产物；验收针对原始症状；workaround 进验收阻塞项并写明何时失效；对方的根因先查对方修了没 |
| T15 | **交付物被替换**（分析 / 设计票被做成修复 / 建设） | 查任何东西前先写「交付 = ___」；「我们没有 X」放观察栏，不进范围和前置条件；分析票的模板没有修复栏；后续建设另开票 |
| T16 | **按话题派单，而不是按真正动手的人** | owner = 「下一个动作是什么、谁的手、叫什么名字」；列出的每个角色都要有第一个动作，否则删掉；没有代码入口更要点名一个人；按根因落点路由 |

**结构性偏差的通用解法**：「必填字段 + 单向禁令 = 稳定偏差」（只有根因字段 + 只禁止说『设计如此』→ 一切都成了 bug）。
修法是补第三个合法出口：「未决 → PM」「已观察 N 个，全量未验证 + 方法」。

## C. 铁律

**证据**
1. 每条断言指向一个验证产物；无产物 = ⚠；任何 ⚠ 阻止进入「修复是…」。
2. 弱链定律：第 N−1 步是 ⚠，N 及之后全部作废；没到不可再分的源头前不停。
3. 「那里找不到 X」也是断言，自己验证。
4. 撤回假设要和提出假设一样的证据。
5. 解释到数：机制只有在数量上闭合差额时才算数，否则只是线索。
6. 继承来的报告一律 ⚠。
7. 逻辑自洽 ≠ 正确；链越长越要复查第一个前提。

**状态与时间**
8. 先排除进行中，再说失败。
9. 新鲜度是算出来的（`lag_days`），不是日期字面量；快照不能反驳历史。
10. 先找断点再下结论；存活者决定事件类型。
11. 「从没配过」和「被改掉了」是两个 owner、两种修法，要看变更历史。
12. 登记 ≠ 生效 ≠ 已回填。

**层与因果**
13. 配置状态先于代码状态，回滚对照是硬闸。
14. 版本没变 → 查输入和参数（包括从不「变」的冻结离线值）。
15. 同一层被证伪两次 → 换层。
16. 机制存在 ≠ 机制导致；旁支发现要达到主因证据标准，否则标线索。
17. 根因要有执行者；按根因落点路由。

**权限与措辞**
18. 「是 bug」与「不是 bug」是同一条越权线；写修复段落 = 已经做了定性。
19. 每个开放项先分象限：事实 → 自己查 · 故障 → 技术 owner · 口径 → PM + owner（只给选项）· 需求 / 排期 → 提出人 + PM + 交付 owner · 客户措辞 → 现在就自己写。
20. 自创阈值 / 默认值 / 范围 / 日期 = 替别人做决定。
21. PM 的「设计如此」只关闭客户预期那一半，不关闭你发现的缺陷。
22. 未证明机制前，永远不要让客户去改东西。

**范围与结案**
23. 范围按根因层算，工单是下限；范围是独立断言。
24. 根因已证 ≠ 结案。
25. 厂商控制的修复是独立的一层。

**工程卫生**
26. 最小 diff，不顺手重构；跨别人的服务 → 侦察后交接。
27. 「跑不了 / 看不到 / 排队 / 拒绝」→ 先查环境，再查逻辑。
28. 文档里有 ≥2 段「更新 / 更正」→ 重写干净，归档 v1。
29. 用代码注释锁定不变量。

## D. 反复用到的判别手法

- **反解报告的数字**：在几个候选窗口 / 口径下算，直到某一个精确命中报告人的数 —— 先锁定口径再查根因。
- **漏斗计数**：给多阶段流程的每一段计数（点出去 / 回调 / 换 token…），比值模式直接选出故障模式。
- **范围矩阵**：「同单元里别的类型正常吗？」×「别的单元里同类型正常吗？」。
- **守恒检验**：总数不变 + 分布变了 = 错分而不是膨胀，影响是展示层面的。
- **合成探针**：一个不涉及真实用户、走故障路径的廉价请求，同时用作首次分诊、上线后验证和定时监控。
- **反复告警的分代**：每次触发都从明细行重算告警值、按维度拆形状；已知形状对应已知代，未知形状 = 新的一代。不许抄上一次的结论。
- **「多入口时扇出」**：一个澄清问题定位不了服务时，并行查所有候选服务，锁定有命中的那个；先收窄过滤条件，再放宽时间窗；先日志后代码。

# Playbook · 知识系统：memory、KB / SOP、反例、校准、自我改进

---

## 1. 四层知识，各放各的

| 层 | 放什么 | 不放什么 | 位置 |
|---|---|---|---|
| **core**（常驻） | 每轮都用的判断和边界 | 领域事实、案例 | `core/AGENTS.md` |
| **playbook / skill**（按需） | 可泛化的方法、流程、模板 | 个案答案、case 编号 | `playbooks/`、`skills/` |
| **KB / SOP**（领域） | 领域规则（编号、只追加）、FAQ、路由表、反例、演练 | 密钥 | `<知识库根目录>/`（本地真源）+ 云端镜像（由领域 pack 指定） |
| **memory**（agent 自己记的） | 我的偏好、纠正、项目约束、外部资源指针 | 代码里看得出来的、git 历史、会话临时状态 | runtime 自带（Claude：`~/.claude/projects/*/memory/`） |

memory 是 **SOP 的暂存区**：一条经验先进 memory，有第二个独立案例后提升为 SOP 规则，memory 里只留指针 + 3–5 条要点。

## 2. 一条 memory 的标准形状

```markdown
---
name: <kebab-case 主题>
description: <一行，用于判断相关性>
metadata:
  type: user | feedback | project | reference
  verified: <YYYY-MM-DD>        # 版本相关的事实必须有
---
<一条判据 / 事实>
**Why:** <日期 + 事件，谁说的>
**How to apply:** <下次遇到什么情况、具体怎么做>
关联：[[其他 memory]]
```
- **一事一文件，按主题而不是按启动目录**。同一主题散在 3–4 个项目目录里是现在最大的问题（见 `research/memory-hygiene.md`）。
- 文件名就是判据：`<症状>-is-<根因>`，索引可以当诊断查找表用。
- `MEMORY.md` 索引每行一句（<150 字）；索引不复述正文，否则会和正文漂移。
- 推翻旧结论：**改正文 + 改文件名 / 索引**，旧结论折叠到「已推翻」小节，不要让读者先读到错的。
- 版本相关的事实（CLI 参数、API 形状）写「在版本 X、日期 Y 验证」，定期复查。
- 事故流水账（一个告警的 20 次触发记录）不是 memory：拆成「一份蒸馏后的判据 memory + 一份事件日志文件」。
- **密钥绝不进 memory**：只记「在哪里」（`~/.config/x/api_key`、keychain 条目名、zshrc 里的变量名）。
- 不要指向 `/tmp` 这类会被清掉的路径。

## 3. KB / SOP 的架构（领域无关模板）

```
<知识库>/
  sop/
    general-debug.md          顶层路由 + 通用循环：入门三问、FAQ 快查、先验证再断言清单、
                              编号规则（只追加）、分诊类、主循环、出口模板、结案模板、反模式、
                              案例库、维护元数据（已吸收会话 / 观察中 / 规则命中频次）
    <oncall>-control-map.md   告警 → 领域路由、误报闸（方法 + 已知列表）、结案闸、严重度 / SLA
    owner-routing.md          领域 × 范围 × 谁修 × 谁拍板 + 边界备注 + 已知空缺
    <domain>-debug.md × N     每个领域：三问、分层对账、范围隔离、FAQ、按读者的写作模板、案例附录
    counterexamples/          反例（README + 带日期的事实类反例 + 去标识的 *-drill.md）
  case-index.jsonl            每份调查报告一行，带评级（默认 / 正确 / 失败）、方向、标签
  corrections/corrections.jsonl   bot 结论 vs 人的纠正（bot_conclusion / human_correction / owner_correction / lesson）
  calibration-suggestions/    每个被纠正的 case 一份闭环校准报告
```
- **SOP 只追加**：不改号、不重写别人的规则；新编号 = 所有来源的 max + 1（并行 PR 会撞号，附录号也会撞）。
- 规则带出处（日期 + case），跨 SOP / skill / 路由表按编号引用，一处修好处处生效。
- 本地 `.md` 是真源，改完**同步更新云端镜像**；只在云端的内容不要覆盖删除；镜像发布前让我确认。
- FAQ 的答案是快照不是真理；命中只是起点假设。
- 用 grep 按章节取，不要整篇喂进上下文。

## 4. 反例库（从错误里学，但不背答案）

四类，各有固定写法：
- **误报类**（设计行为被当故障；结论是公司级事实）→ 可写结论。`YYYY-MM-DD-<症状>-误判成<错误结论>.md`：TL;DR 警告 · ❌ 错的路径 · 🔍 为什么错（信号 / 我怎么读的 / 它实际证明什么）· ✅ 正确做法（指向 SOP 章节）。
- **因果类**（真故障，因果搞错）→ **演练文件** `<主题>-drill.md`：无日期、去标识（X/Y、T0 偏移）、原错误结论原文、空白结论表 + 自检问题、「判据会把你带到哪」，**永远不写最终答案**，不镜像到云端。
- **错结案类**（分析对，状态 / 时态 / 验收 / 执行者错）→ 可写结论，引用错误原句。
- **评级类**（原因对，范围 / 优先级 / SLA 错）→ 引用误导人的规则原文 + 修正后的判据。

索引列：日期 · 症状 · 误判成 · 类型 · 该用哪条判据 —— **从不写「真相」**。能认出卡片然后取回上次答案的索引训练的是查表，不是诊断。
每份反例自评一句：「是规则的错，不是执行的错」，并列出「现在的判据」改了哪些文件。

## 5. 校准（改规则 / prompt 的 CI）

1. **金标准**：把我复盘过的历史 case 重建成**线上同形**的输入（触发时刻截断上下文，不泄露未来信息）。标注口径写下来并注日期；例外写在构建脚本顶部（OVERRIDE / NOTE_LEVEL / EXCLUDE / TRIGGER_FROM），每条带理由。原始数据不进 git。
2. **用线上同一条流水线重放**，逐条比对，写报告。
3. **稳定性**：连续 N 轮全新运行（不走缓存）都 0 不一致才算过 —— 模型有随机性，单轮过不算数。
4. **不背答案**：规则写成可泛化的描述，不写 case 编号或个案答案。
5. **对照**：比较新旧知识库必须同 harness、同判卷；先在旧版本上跑同一张卷，再说「退步了」。抽样要分层（重复告警会被均匀抽样过度代表）。
6. **没有靶子不改**：只有「失败 + 人确认过的正确答案」才触发改动；验收待定 ≠ 判错（待定 15 次里 11 次，会产出伪教训）。

## 6. 闭环：从会话 / 纠正里吸收教训

```
工单 / 告警 → 调查报告（文档）→ case-index（评级）
           → 有人纠正？→ corrections.jsonl
                       → 找到误导的规则 → 追加规则 / 闸 / case
                       → 干净子 agent 重跑直到命中人给的答案
                       → 反例文件（事实类）或演练（因果类）
                       → skill 铁律 + description 关键词更新
                       → 路由表边界 / 已知空缺更新
会话扫描（distill-lessons）→ DIFF 提案 → 我确认 → SOP 追加 → 「已吸收会话」
单证据的模式 → 「观察中」→ ≥2 例后提升为规则
规则命中频次表 → 长期为 0 的规则考虑退役
```
- 按**集合差**找新会话（已吸收集合之外的），不按时间窗；内容从原始 transcript 抽，不凭标题猜。
- 每个候选抽 5 个字段：症状 / 转折点 / 根因 / 模式签名 / 路由目标。信息量低的跳过。
- 分类：命中已有规则（+1 并加 case）/ 细化 / 新规则（需 ≥2 证据，否则「观察中」）/ 路由修改 / 新 skill 候选。
- **永远先 DIFF，等确认再写**；我没回复就不动文件。回复语法固定：`all` / `cases only` / `1,3,5` / `skip`。
- 被纠正的那句 `bot_conclusion` 要读，不只读 `lesson`：lesson 说的是不要做什么，不是要去找什么。
- 人的纠正在回答模块运行前吸收，子 agent 才能看到。人（[他人]）的话权重最高；bot 自己（以我身份发的）的话权重低，否则会自说自话。

## 7. 维护节奏

- 每次被纠正：当场修 memory / SOP，不等「以后整理」。
- 定期（例如每周）跑一次 memory 卫生检查：重复、矛盾、过期的状态声明（「待下次运行核实」已过期）、悬空链接、密钥、索引漂移。
- 重复的手工修复做了 3–4 次 → 写通用 SOP。
- 文档里有 ≥2 段「更新 / 更正」→ 重写干净，归档 v1。

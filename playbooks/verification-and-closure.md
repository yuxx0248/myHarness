# Playbook · 验证、验收与结案

适用：要下结论、发报告、交接、宣布「修好了 / 完成了」之前。

---

## 1. 证据标准

- 每个业务值都带证据（来源 id、URL、查询参数、时间戳），让验收者不必信任实现者就能复查。
- 证据类型要和断言匹配：数据断言 → 真实查询行；结构断言 → schema；行为断言 → `file:line` 的写入点 + 日志；
  人的决定 → 消息 id + 时间；UI 断言 → 截图（附身用户 / 本地 UI / 预发环境）。
- 置信度要显式写：`✓ 已实证` / `⚠ 未证实` / `实测（非预测）` / `模拟（非真实路径）`；推断出来的比例写「含推断，勿精确引用」。
- 抽样还是全量要写明。
- 自己写错了的结论**保留可见的更正记录**，而不是悄悄删掉。

## 2. 验收标准（事先定，不事后找）

- 每条验收：编号、验证什么性质、输入 / 步骤、**可客观检查的通过条件**（数字、相等、计数、包含）、需要的证据。不接受「基本没问题」。
- 验收记录要写：构造的条件、实际结果、**为什么这个结果证明了性质，而不是碰巧通过**。好的测试直接复现原 bug 的触发条件。
- 判定：任何一条 FAIL → 整体 FAIL；缺证据 → FAIL；重跑不稳定 → FAIL。
- **验收对象 = 报告人原始症状的那句话不再成立**。开关打开、`status=active`、额度恢复只是前提条件。验收条数 = 报告人列出的症状数，不是根因数。
- 「完成」的条件：PR 已合 + 已部署 + **在该环境里**按每个独立原因重新验证；症状由 N 小时周期产生的，观察窗口要 > N 小时（「刷新一次看起来好了」≠ 修好）。
- SLA 截止日只是响应期限；「最早可验收日」单独写，可以是「未知（等厂商）」。
- 改动在分支上 ≠ 修好：确认线上实际跑的那份（部署目录、软链目标、镜像 digest）包含了这次修改。

## 3. 独立验收

- 实现者 ≠ 领域验收者 ≠ 端到端验收者。验收者只看 PR、EVIDENCE、计划，自己重跑每一条。
- agent 起草的金标准集要人抽查过才能用，否则就是被测能力在给自己打分；同一金标准上跑旧逻辑作为基线。
- 需要人做的事（轮换凭据、开权限、抽查、审批、拍板）单独列出，依赖它们的用例在完成前不能 PASS。
- 改知识（SOP / skill / prompt）的验收：用**干净的子 agent，只给原始输入、不给答案**重跑；用同一考卷、同一判卷方式对照旧版本；
  答案在知识库里能被 grep 到的通过不算数。

## 4. workaround ≠ 修复

- workaround 降低紧急度，永远不结案，也不缩短验收。
- 要写进验收阻塞项：它不满足哪一条验收、什么时候失效。不能放在客户消息的「下一步」位置（读起来像已解决）。
- 给出的逃生路径必须自己证明可用，不要推荐自己报告里已经证明走不通的路。
- 真正解决问题的配置回滚**不是** workaround，属于正式修复那一档。

## 5. 四态状态位（写在报告最前面）

| 状态 | 允许的措辞 |
|---|---|
| `根因待证` | 「怀疑」「正在验证」 |
| `根因已证 · 修复待执行`（默认） | 「已定位」「需要 <具名人> 做 <动作>」 |
| `修复已执行 · 待验收` | 「已部署，验收条件：<可运行的检查>」 |
| `已验收闭环` | 只有这一态能说「已修复 / 完成 / Investigation complete」 |

把「已修复」再拆细：历史已补 / 机制未修 / 每周会复发。

非故障类交付物用自己的状态位：分析票 → `分析已交付` / `分析已交付·待 PM 定性`；需求票 → `诊断 + 范围选项已交付·待排期（由 PM / 交付 owner 定）`。

## 5.5 以我身份发出的消息

- 我对某条消息说「发」= 授权**这一条**；仍要先过 §6 结案闸，措辞用我的口吻。
- playbook `autonomy-and-triage.md` §5 的串联闸是给**无人值守 / 自动**发言用的；我明确授权的单条消息不需要全部满足，但涉及承诺时间、改客户可见结论时仍要在发前提醒我一句。

## 6. 结案闸（发出任何结论前逐条过）

1. 状态位在最前面。
2. 结尾措辞和状态位一致（没有对未完成动作用完成时态）。
3. 每个「已…」都有产物撑着。
4. 验收条件可运行，且针对原始症状。
5. 执行者具名（不在自动 @ 名单里的要标出来需要手动拉）。
6. 厂商闸：修复开关是否在外部厂商手里。
7. 没有无依据的「无需处理 / 会自愈 / 已明确排除」。
8. 客户可见的每一句话都在回答客户的问题。
9. 共享基线还是私有线路，爆炸半径有实测数字。
10. 「谁的手会动？」+ 对方那边的修复进度已查。

## 7. 交付物形态

- 实质性调查 → 可分享文档，每一步三件套：**Query（完整可重跑）+ 结果（表格 / 关键行）+ 解读（证明或否决了哪个假设、为什么走下一步）**。
  文档链接回写到案例库。只有 ≤5 分钟且纯内部的小事可以只在聊天里给结论。
- 聊天：「问题 / 原因 / 修复」三句话 + 链接。
- 功能 / 修复类：本地或预发 UI 截图作为证据；上线后再验一次（可以给自己定个 timer 回来查）。
- 问题 / 修复写成**故事卡**而不是宽表格：问题是什么 / 为什么不对 / 为什么这么修 / 修好后的结果 / 怎么验证。测试表格另列。
- 同一份文档里已经有 ≥2 段「更正」时，重写成干净的最终版，只保留正确结论（「用正确分析覆盖原文档」）。

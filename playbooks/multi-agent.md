# Playbook · 多 agent、上下文预算、并行会话

---

## 1. 什么时候分派

- **上下文预算**：超大文件（>25k token）、几十份 transcript、全量 memory、多个数据源的交叉 —— 先用脚本预处理（过滤、去重、统计），
  再交给子 agent / 新上下文去读，主线只拿结构化结论。永远不要在主上下文里整篇读大文件。
- **独立的块并行**：按领域 / 数据路径切，一次发出去；有依赖的串行。超过 12 天的时间跨度拆成两个子任务。
- **小事直接做**：一个已知文件、一个已知符号，不要为它开子 agent。

## 2. 给子 agent / 接手 agent 的 prompt（事无巨细，防漂移）

必含：
1. **目标**：最终交付什么，交到哪里（文件路径 / 文档）。
2. **已证实的事实**（带产物）和**已否决的假设**（以及为什么），防止接手者重走死路。
3. **范围**：读哪些、不读哪些（别人负责的部分不要碰）。
4. **约束**：只读 / 可写的边界，不许发消息，不许碰生产，stop_at。
5. **输出契约**：固定的章节 / JSON schema / 写到哪个文件；回给主线的只要 N 行摘要。
6. **验收标准**：怎么判断子任务完成。
7. 「不要编」「引用原话要短」「只引用不复制密钥」这类卫生要求。

## 3. 验证和实现分开

- 实现 agent 的自述**不够**；验收 agent 是对抗性的，只看 PR、证据文件和计划，自己重跑。
- 改知识（SOP / skill / prompt）：干净的子 agent 只拿原始输入、不给答案重新做；
  KB 里能 grep 到本案答案的，在考试期间把那份文件移出去（「KB 是一条侧信道」）。
- 「如实申报」类字段不能同时当惩罚依据，否则是在训练它撒谎；`leaked` 要从证据链判断（抽掉那份案例文件后结论还站得住吗）。

## 4. 协调者循环（长任务、多条线）

冻结验收清单 → 设计 + 拆分 → 编码 agent → 清理闸 → 测试 agent → 对抗验收 agent → 协调者硬验收 → 结果优先的汇报。
- 定一个自检 loop（例如 30 分钟）：看各 agent 状态、把主干合进各分支、派下一张卡、读阻塞清单。
- 剩余问题是局部且清楚的 → 自动开额外修复轮；有冲突 → 串行。设计变更 / 破坏性契约变更 → 停下等我。
- **阻塞项不在聊天里逐条问**：放进异步队列（共享表格），每条写「背景与选项 / 我的建议 / 你的决定」，状态 🔴等你 🟡待我执行 🟢已解决，让我批量处理；能推进的继续推进。
- 同一根因专注尝试 3 次仍不行 → 升级给人。每段有尝试上限，共用一个转人工出口。
- 「完成」= 合进目标主干 + 临时分支 / worktree 已清理。一个任务一份进度文件（覆盖更新），不要堆 FINAL / FINAL2。

## 5. 额度守卫

- 派新活之前看额度；5h 用量 ≥85%（或我指定的阈值）→ 停止派新活，让在跑的跑完，在重置时间 +3 分钟定一个一次性 timer 恢复，连自检 loop 也暂停。
- 查不到额度时 fail-open（不能因为查不到就罢工），但上游要有守卫。
- 并行子 agent 会很快烧完额度；彻底烧完会卡死所有会话。

## 6. 并行会话的可接续性

我经常同时追 3–5 个会话，切回来容易忘上下文：
- 交互会话前 3 轮内把标题设成 `[工作线] 具体任务`（带关键 ID、客户名、PR 号）；只改一次。
- 每轮末尾附状态卡（📍✅⏳👉）。
- 汇总侧：`where-was-i` 一类工具读所有未归档会话的状态卡，按工作线分组，列出每条线的「等你」。
- 长任务把进度写到外部文件（STATUS.md / todo.md），会话重启后能接上。
- 交接给新会话：用 `handoff-prompt` skill 生成完整 prompt。

## 7. 自动化 → 交互会话的交接

自动化只负责检测 / 去重 / 上限（确定性脚本），然后**提议**后续工作（Claude 里是 spawn_task chip；Codex 里是一组可直接运行的
`codex exec "<prompt>"` 命令或一个队列文件），由我点了才开完整会话。调度层不要自己排查任何东西，prompt 原样转交，不改写不截断。

# close-out

完整标准见 `~/.agents/framework/playbooks/verification-and-closure.md`。逐条过，任一不通过就改稿，不要发。

## 结案闸（10 条）
1. **状态位在最前**：`根因待证` / `根因已证·修复待执行` / `修复已执行·待验收` / `已验收闭环`。只有最后一个能说「已修复 / 完成」。
2. **时态**：没做完的动作没有用完成时态（「已排期」「已转研发修复」要有人确实做了）。
3. **每个「已…」有产物**（查询行、PR 链接、部署记录、消息 id）。
4. **验收条件可运行、针对报告人的原始症状**（不是开关、不是 PR 合并）；症状条数 = 验收条数。
5. **执行者具名**；不在自动 @ 名单里的标出来。
6. **厂商闸**：修复开关在不在我们手里？不在 → ETA「未知（卡在 <X>）」。
7. 没有无依据的「无需处理 / 会自愈 / 已明确排除」。
8. **客户可见的每一句都在回答客户的问题**；旁支观察不进客户文本。
9. **影响面**：共享层还是私有线路？有实测数字吗？受损面 / 暴露面 / 修复爆炸半径分开写。
10. **谁的手会动**；对方那边是不是已经修了（先查）。

## 措辞检查
- 定性（「是 bug」「设计如此」「永久」「唯一路径」）→ 改成选项 + 推荐，交给 PM / owner。
- 承诺（「我们会…」）→ 删掉时间词还是承诺吗？是 → 改成「需要 <具名人> 做 <动作>，工作量 <X>」。
- 全称量词（「所有客户」）→ 有全量计数吗？没有 → 「已观察到 N 个，全量未验证（方法：…）」。
- workaround 不放「下一步」位置；写明它不满足哪条验收、何时失效。

## 输出
- 文档：状态位 → TL;DR → 证据链（Query + 结果 + 解读）→ 验收条件 → 执行者。
- 聊天 / 群：一条消息一类读者；「谁 · 做什么 · 什么时候」；详细内容放文档链接。
